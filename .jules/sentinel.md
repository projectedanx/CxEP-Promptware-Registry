## 2024-05-24 - [Critical Supply Chain Vulnerability & Command Injection]
**Vulnerability:** Found a reference to a nonexistent GitHub Action (`OrRosenblatt/validate-yaml-action@v1.0.1`) which presents a severe repojacking risk. Additionally, the previous configuration utilized `${{ steps.changed-files.outputs.all_changed_files }}` directly inside a run script, exposing the CI pipeline to command injection.
**Learning:** External actions must be verified for existence, trustworthiness, and maintenance. Directly interpolating untrusted variables within a run script poses a major security hazard.
**Prevention:** Avoid third-party actions when standard tooling (like Python's `check-jsonschema`) suffices. When passing data into shell scripts within a workflow, always bind the context to an environment variable and use the shell's secure variable expansion mechanisms instead of direct interpolation.
## 2024-05-25 - [Medium Severity: Flag Injection via Filenames]
**Vulnerability:** Found a flag injection vulnerability in GitHub actions script that processes filenames provided by `tj-actions/changed-files`. When files begin with a `-`, they might be parsed as flags instead of filenames (e.g. `yamllint -h.yml`), allowing attackers to potentially execute code or leak data. Furthermore, missing `diff_filter: ACMRT` led to executing commands on deleted files, leading to errors.
**Learning:** Any dynamic values controlled by users (like filenames) passed to bash scripts without the end-of-options marker `--` could be misconstrued as flags.
**Prevention:** Always use `--` before dynamic arguments passed to standard unix/linux utilities (e.g., `yamllint -- "$file"`) and configure `diff_filter: ACMRT` for `tj-actions/changed-files` appropriately to handle deleted files gracefully.
## 2024-05-26 - [Critical Security: Missing Pattern Constraint on check_id]
**Vulnerability:** The `check_id` field in the `SELF_TEST` block of `schemas/prp_schema.yml` lacked a regex pattern constraint. This could allow malicious actors to inject path traversal sequences or command injection payloads if the `check_id` is later used in downstream shell scripts or file operations.
**Learning:** All string identifiers in schemas that might be processed by external systems or scripts must enforce strict regex pattern constraints (e.g., `^[a-zA-Z0-9_.-]+$`) to prevent injection vulnerabilities.
**Prevention:** Always add `pattern` constraints to string fields representing IDs, filenames, or other critical identifiers in JSON/YAML schemas.
## 2024-05-27 - [High Severity: Missing Pattern Constraints on Repository References]
**Vulnerability:** The `REQUIRED_REPOSITORY` object in `schemas/prp_schema.yml` lacked regex pattern constraints on the `name` and `initial_state` fields. If downstream CI/CD pipelines or automated execution tools consume these fields to perform `git clone` or `git checkout` operations, malicious prompt authors could inject command sequences (e.g., `repo; rm -rf /`) or path traversal payloads (`../../`).
**Learning:** Any schema field that might be used as an argument to shell commands or file path operations by consuming applications MUST enforce strict regex pattern constraints to neutralize injection risks.
**Prevention:** Apply whitelist-based regex patterns (e.g., `^[a-zA-Z0-9_.-]+(?:/[a-zA-Z0-9_.-]+)?$`) to all external resource references in schemas to prevent injection via untrusted configuration data.
## 2026-04-06 - [High Severity: Unconstrained Parameter Injection in SELF_TEST]
**Vulnerability:** The `params` object inside the `SELF_TEST` blocks in `schemas/prp_schema.yml` lacked constraints on the string values it could accept. As these parameters (like `schema`, `artifact`, `target`) often map to file paths or arguments in backend validation scripts, an attacker could supply payloads like `../../etc/passwd` or command flags like `-h` to compromise the validation pipeline.
**Learning:** Any schema section allowing arbitrary key-value pairs (like `params`) that are subsequently consumed by execution environments must still enforce strict validation on the values.
**Prevention:** Use JSON schema properties like `additionalProperties` with a strict `pattern` constraint (e.g., `^[a-zA-Z0-9_.-]+(?:/[a-zA-Z0-9_.-]+)?$`) to ensure that any un-modeled keys map to safe, injection-proof string values, while explicitly defining exceptions like `message`.
## 2026-04-07 - [High Severity: patternProperties Bypass in SELF_TEST checks params]
**Vulnerability:** The `params` object inside `SELF_TEST` blocks utilized `patternProperties` to restrict values for expected keys but lacked `additionalProperties: false`. This allowed an attacker to completely bypass validation by supplying arbitrary, un-modeled keys (e.g., `malicious-key!: "injection payload; rm -rf /"`) containing malicious payloads.
**Learning:** `patternProperties` in JSON schemas does not restrict keys that do not match the provided regular expressions. If `additionalProperties` is not set to `false`, un-modeled keys and their unvalidated values will be accepted.
**Prevention:** Always pair `patternProperties` with `additionalProperties: false` to enforce strict validation and block unexpected keys from bypassing constraints.
## 2026-04-08 - [High Severity: Missing additionalProperties Constraint in REQUIRED_REPOSITORY]
**Vulnerability:** The `REQUIRED_REPOSITORY` object in `schemas/prp_schema.yml` contained `pattern` constraints on its properties but lacked `additionalProperties: false`. This would allow an attacker to bypass validation by providing un-modeled keys with arbitrary, unvalidated string values (e.g., `malicious_key: "rm -rf /"`), potentially leading to command or path injection if the schema consumer processes these extra keys.
**Learning:** Like `patternProperties`, defining explicit properties in JSON schemas does not restrict keys that are not explicitly defined. If `additionalProperties` is not set to `false`, un-modeled keys and their unvalidated values will be accepted.
**Prevention:** Always set `additionalProperties: false` in object definitions to enforce strict validation and block unexpected keys from bypassing constraints, especially when the object defines configuration that is consumed by execution environments.
